## TL;DR

The source recommends creating and testing analyzers in the visual Content Understanding Studio in most scenarios. (SRC-29 L216) It then shows the API alternative: define the fields to extract or generate in a JSON schema, create the analyzer with `ContentUnderstandingClient.begin_create_analyzer`, or submit the JSON by REST `PUT` and poll the `Operation-Location`. (SRC-29 L216–230)

## Key claims

- In most scenarios, analyzers should be created and tested with the visual interface in Content Understanding Studio. (SRC-29 L216)
- Analyzer creation through the API is useful when submitting a JSON schema definition for desired content fields. (SRC-29 L216–218)
- Analyzer schemas define fields to extract or generate from a content file. (SRC-29 L218)
- The example schema is based on the prebuilt document analyzer and describes `ContactName` and `EmailAddress` fields on a business card. (SRC-29 L221)
- The example fields are string data types expected to be extracted from a document, not generated by inference about the document. (SRC-29 L221)
- The `models` object specifies the generative models the analyzer uses for processing. (SRC-29 L221)
- The sample schema is deliberately minimal, and real analyzer definitions may include more fields, field types, configuration settings, and a sample document. (SRC-29 L222–223)
- The Python SDK `ContentUnderstandingClient` provides `begin_create_analyzer` for asynchronous analyzer creation. (SRC-29 L224–225)
- REST analyzer creation submits JSON data as a `PUT` request to the endpoint with the API key in the request header. (SRC-29 L228–229)
- The REST `PUT` response includes `Operation-Location`, a callback URL for polling status with `GET`. (SRC-29 L230)

## How it works

The author starts with a design recommendation: use Content Understanding Studio visually for creating and testing analyzers in most scenarios. (SRC-29 L216) The code-oriented path begins with an analyzer definition: a JSON schema containing the fields the analyzer should extract or generate from a content file. (SRC-29 L216–218) In the business-card example, the schema uses a prebuilt document analyzer, names two string fields, and indicates those strings should be extracted from text present in the document. (SRC-29 L221)

After the schema exists, the Python SDK path uses `ContentUnderstandingClient.begin_create_analyzer` to handle asynchronous creation. (SRC-29 L224–225) The REST path sends the JSON schema to the endpoint by `PUT` with an API key header; the response supplies an `Operation-Location` callback URL for polling with `GET`. (SRC-29 L228–230)

## Code and API patterns

The source names these API patterns, but the captured code blocks contain only language and copy markers, not code bodies. (SRC-29 L219–220; SRC-29 L226–227; SRC-29 L231–233)

- SDK client: `ContentUnderstandingClient`. (SRC-29 L224–225)
- SDK method: `begin_create_analyzer`, which handles asynchronous analyzer creation. (SRC-29 L224–225)
- REST method: `PUT` with JSON schema data and an API key header. (SRC-29 L228–229)
- REST polling: use `Operation-Location` from the response header as the callback URL for `GET` status checks. (SRC-29 L230)

## Key terms

- **Analyzer schema** — a JSON-defined set of fields to extract or generate from a content file. (SRC-29 L216–218)
- **Extracted field** — in the example, a value expected to already exist in the document and be read from it. (SRC-29 L221)
- **Generated field** — a field type implied by contrast: not read directly from the document, but generated by inferring information about it. (SRC-29 L221)
- **`models` object** — the part of the analyzer definition that specifies the generative models used for processing. (SRC-29 L221)
- **`Operation-Location`** — the response header containing the callback URL used to poll analyzer-creation status. (SRC-29 L230)

## Decision boundaries and exam cues

- **Inference:** Prefer Content Understanding Studio when a scenario emphasizes creating and testing analyzers visually, because the source says this is what you should consider in most scenarios. (SRC-29 L216)
- **Inference:** Prefer API-based creation when the scenario provides or asks for a JSON schema definition of desired content fields. (SRC-29 L216–218)
- **Inference:** For SDK code, look for `ContentUnderstandingClient` and `begin_create_analyzer`; for REST code, look for `PUT`, an API-key header, and `Operation-Location` polling. (SRC-29 L224–230)
