## TL;DR

Dynamic tool discovery lets agents find and use external tools at runtime instead of requiring every integration to be manually registered and maintained (SRC-233 L216). MCP supports this by letting an MCP server act as a live catalog that exposes tools an agent can understand and call (SRC-233 L223). The pipeline is server hosts tools, client discovers tools, and the Azure AI Agent uses the available tools to respond to user requests (SRC-233 L229-L232).

## Key claims

- Registering, managing, updating, and integrating agent tools can become complex and time-consuming as tool ranges grow (SRC-233 L216).
- MCP provides dynamic tool discovery, interoperability across LLMs, and standardized security as benefits for AI agents (SRC-233 L218-L221).
- Dynamic tool discovery removes the need for hardcoded knowledge of every external tool by having the agent query a centralized MCP server (SRC-233 L223).
- Tool changes can be made centrally without modifying agent code, and agents can use the latest tool version (SRC-233 L225-L226).
- MCP shifts tool-management complexity away from the agent and into a dedicated service (SRC-233 L227).
- MCP servers expose functions as tools with the `@mcp.tool` decorator, and clients fetch those tools dynamically (SRC-233 L229).

## How it works

The source presents MCP discovery as a runtime catalog pattern: an MCP server exposes tools, a client connects to the server and fetches them, and the client generates function wrappers that are added to the Azure AI Agent's tool definitions (SRC-233 L229). The source then states the three-step pipeline explicitly: server hosts available tools, client discovers them, and the Azure AI Agent uses them for user requests (SRC-233 L230-L232).

The source's maintenance model is centralized: tools are added, updated, or removed in the MCP server rather than in each agent's code (SRC-233 L225-L227). The claimed benefits are scalability, modularity, maintainability, and flexibility, especially where tools evolve quickly or different teams own APIs and services (SRC-233 L235-L239).

## Code and API patterns

The unit names the server-side decorator and client-side wrapper generation but does not provide executable code (SRC-233 L229). The only code-form term is:

```text
@mcp.tool
```

The source says functions exposed with `@mcp.tool` become tools that MCP clients can fetch dynamically (SRC-233 L229).

## Key terms

- **Dynamic tool discovery:** A mechanism that lets an AI agent discover available external tools without hardcoded knowledge of each tool (SRC-233 L223).
- **MCP server:** A centralized live catalog that exposes tools the agent can understand and call (SRC-233 L223).
- **Tools:** The source describes tools as an MCP primitive that lets servers expose executable functionality to clients (SRC-233 L229).
- **Function wrappers:** Generated by the client and added to the Azure AI Agent's tool definitions (SRC-233 L229).

## Decision boundaries and exam cues

- **Inference:** Choose MCP discovery over manual API integration when a scenario stresses frequent tool changes, many APIs, or different teams owning services, because the source emphasizes central updates and fast-changing tool environments (SRC-233 L225-L239).
- **Inference:** If the scenario says the agent should switch or evaluate LLMs without reworking tool integrations, MCP is relevant because the source lists interoperability across LLMs as a benefit (SRC-233 L220).
- **Inference:** If the scenario asks where complexity belongs, MCP moves tool-management complexity into the dedicated server rather than the agent (SRC-233 L227).
