## TL;DR

A functioning MCP setup has an MCP server that hosts the tool catalog and an MCP client that fetches those tools and makes them usable by the agent (SRC-108 L216). The server can be initialized with `FastMCP("server-name")`, which uses Python type hints and docstrings to generate tool definitions served over HTTP (SRC-108 L218). The client discovers tools with `session.list_tools()`, wraps them as async functions that call `session.call_tool`, bundles them into `FunctionTool`, and registers the result with the agent (SRC-108 L220-L233).

## Key claims

- Dynamic connection first requires both an MCP server and an MCP client (SRC-108 L216).
- The MCP server acts as a registry for tools your agent can use (SRC-108 L218).
- `FastMCP("server-name")` initializes an MCP server, and FastMCP uses Python type hints and docstrings to generate tool definitions (SRC-108 L218).
- A standard MCP client bridges the MCP server and Azure AI Agent Service (SRC-108 L220).
- The client discovers tools with `session.list_tools()`, generates Python function stubs, and registers those functions with the agent (SRC-108 L220-L223).
- The client can invoke an MCP tool with `session.call_tool(tool_name, tool_args)` (SRC-108 L226).
- Wrapped async functions are bundled into `FunctionTool` and registered to the agent's toolset (SRC-108 L226-L233).

## How it works

The source separates tool management from agent logic. The MCP server owns the definitions; because they live on the server, tools can be updated or added without modifying or redeploying the agent (SRC-108 L218). The MCP client then initializes a session, connects to the server, discovers available tools, generates stubs, and registers them with the agent (SRC-108 L220-L224).

Runtime invocation uses the MCP session: each async wrapper invokes `session.call_tool`, the wrappers are bundled into `FunctionTool`, and `FunctionTool` is registered into the agent toolset so the agent can use natural language to call the tools (SRC-108 L226-L234).

## Code and API patterns

The source names these implementation elements (SRC-108 L218-L233):

```text
FastMCP("server-name")
session.list_tools()
session.call_tool(tool_name, tool_args)
FunctionTool
@mcp.tool
```

`FastMCP("server-name")` initializes the server, `session.list_tools()` fetches available tool definitions, `session.call_tool(tool_name, tool_args)` invokes tools, `@mcp.tool` decorates server-side tool definitions, and `FunctionTool` makes the wrapped functions usable by the agent (SRC-108 L218; SRC-108 L226-L233).

## Key terms

- **MCP server:** The registry that hosts the tool catalog and serves generated tool definitions over HTTP (SRC-108 L216-L218).
- **MCP client:** The bridge between the MCP server and Azure AI Agent Service (SRC-108 L220).
- **Function stubs:** Python functions generated by the client to wrap discovered tools (SRC-108 L221-L223).
- **FunctionTool:** The bundle that makes tool functions usable by the agent (SRC-108 L232).

## Decision boundaries and exam cues

- **Inference:** Use this local client/server pattern when the agent cannot directly use a remote managed `MCPTool` object and needs wrappers around discovered MCP tools (SRC-108 L220-L233; SRC-240 L216-L217).
- **Inference:** If a question asks which call retrieves the catalog, choose `session.list_tools()` because the source names it as the discovery call (SRC-108 L221; SRC-108 L230).
- **Inference:** If a question asks why wrappers are async, connect it to nonblocking invocation through `session.call_tool`, because the source says each tool is wrapped in an async function that invokes `session.call_tool` (SRC-108 L226-L231).
